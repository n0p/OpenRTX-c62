# Menu audit

Every menu of the C62's UI, walked in the host simulator, row by row: what each
row shows, and what ENTER (green), P1 and P2 do to it. This is the table the
`c62/menu-audit` pass was built on, and the record of the dead rows it found and
removed.

Generated by `tools/simulator/menu_audit.py`; see "Reproducing the walk" at the
end for the exact commands. The simulator runs the firmware's own UI, menus,
state machine and stores (`docs/SIMULATOR.md`), so a row here is the row the
radio draws.

## How to read it

- **Row** is the label the screen drew; **Kind** is the row's type in the table
  (`int`, `enum`, `toggle`, `info`, `goto`, `action`), which the dump now
  reports. Rows of the fixed Settings pages have no kind: they are the hand
  written lists in `ui.c`.
- **Value** is the right-hand text when the screen was captured.
- **ENTER / P1 / P2** is what the key did: the value it moved the row to, the
  screen it opened, `settings` when the change was written to the settings
  record, `retune` when the receiver moved. `—` means the key changed nothing
  (a row at its limit, or a key that row does not use); `status` is a read-only
  row of a popup, which is what the receiver is doing and not an option.
- **A dead row** would be a row whose three keys change nothing and which is not
  a status row. The list at the end of this file is empty: this pass was the one
  that removed the last ones.

## What the walk found

| # | Where | Dead row / defect | Fix | Commit |
|---|---|---|---|---|
| 1 | Settings ▸ DMR, NXDN, dPMR, P25, YSF, D-STAR, AM, WFM | 22 read-only rows (`QM_INFO`) in a page whose purpose is to change things: `CC`, `TS`, `SYNC`, `CALL`, `TYPE`, `NAC`, `MY`, `UR`, `RPT`, `TXT`, `CH`, `ST`, `LVL`, `SNR`. P1, P2 and green beeped and changed nothing | `qm_page_open()` builds the page from the table without the `QM_INFO` kind; the popup keeps them | `ui: a mode's Settings page lists only the rows that can be changed` |
| 2 | Settings ▸ FM | `CTCSS TX`, `CTCSS RX` and `Cancel CT` were the same two flags as `CTCSS En.` for the second and third time (the popup has one `CTCSS` row) | the page keeps `CTCSS Tone`, `CTCSS En.`, `Bandwidth` | `ui: the FM page keeps one row per tone flag, not three` |
| 3 | Settings ▸ Display, Radio, Audio, Accessibility, FM, M17, TETRA | P1/P2 did nothing in an edit: the pages only answered the arrows, so the same row read one way in the popup and another here | P1/P2 change the value, as everywhere else | `ui: P1 and P2 change the value in a Settings edit` |
| 4 | Settings ▸ Radio, the eleven popups, the tools menu | the accessory port could be set from three screens, and the code for two of them (the `R_PC_PORT` row, `QM_ITEM_PORT`, the docs that still pointed at them) stayed behind after cb779871 | one row, in the tools menu; the leftovers are gone and a test forbids a second row | `ui: the port is one row, and the code for the other two is gone` |
| 5 | tools menu (P1 long) | the tour still declared five rows and failed on the sixth | the tour knows the `Puerto` row and flips it | `sim: a menu audit, and the tour knows the tools menu has six rows` |

Two rows that are **not** dead but are worth knowing about, and were left alone:

- **Menu ▸ Banks and Menu ▸ Channels** open the classic codeplug lists, and the
  C62 links `cps_io_stub.c`: on this radio they are always empty. On the host
  they read `.codeplug`, which a fresh run does not have, so they are empty
  there too. `Channels` is also the name of the tools menu row that opens the
  radio's own bank (which has content). Removing the two rows for builds without
  a codeplug needs a build flag that does not exist yet and would change the
  menu the other targets use; it is a decision, not a menu fix, so this pass
  leaves them declared and documented (`docs/UI.md`, "What the walk found").
- **Menu ▸ Info** is a read-only page by design (`Git version`, battery, RSSI,
  heap): it does not pretend to be an edit page.
- **`AM ▸ STEP`** and **Settings ▸ Radio ▸ Step** both drive the global tuning
  step (the mode's raster also stores `am_step` and re-applies it on entry);
  they are two settings that interact, not one setting written twice.

## Reproducing the walk

The simulator, built the way `docs/SIMULATOR.md` says:

```sh
meson setup build_sim
meson compile -C build_sim openrtx_c62_sim
```

One command per screen, from a clean state (the store and the settings record
are files of the run, so a run starts empty):

```sh
printf 'key GREEN\nkey DOWN\ndump json\nquit\n' | \
  OPENRTX_SIM_HEADLESS=1 SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy \
  XDG_STATE_HOME=$(mktemp -d) OPENRTX_SIM_STORE=$(mktemp -u) \
  build_sim/openrtx_c62_sim
```

The whole audit, which is what produced the table above:

```sh
python3 tools/simulator/menu_audit.py --out /tmp/menu-audit          # all of it
python3 tools/simulator/menu_audit.py --out /tmp/menu-audit \
        --only popup,page --modes DMR                                # one mode
```

and the tour, which is the regression that keeps every declared screen walked:

```sh
python3 tools/simulator/tour.py --out /tmp/tour
meson test -C build_sim "Simulator Menu Tour"
```
